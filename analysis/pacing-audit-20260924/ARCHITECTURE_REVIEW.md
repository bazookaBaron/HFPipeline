# Architecture review — topic button to finished video (2026-09-24)

Scope: read-only stress test of `MOTION_PACING_PLAN.md` against the full prior `VIDEO_AESTHETIC_PLAN.md`, current pipeline, component registry, and the generated hash-collision job `cs-b9d30fa7964c0cf0`. This is a decision and implementation plan, not a pipeline change. The reference measurements are taken from the pacing plan's visual logs; I did not rerun their frame analysis or render a new video.

## Decision

**Keep this repository and the existing HyperFrames, F5-TTS, WhisperX, Gemini, and control-panel stack. Change the *authoring model* inside it.** The current unit called a `scene` conflates a narrative beat, an audio clip, and a mounted visual. The target needs those concepts separated: one continuous narration timeline, many word-timed visual events, and a smaller number of visual hosts that may persist across events. A `v2` contract alongside the existing path is sensible. The proposed 25–40 separately mounted scenes and generic `enter: "continue"` are not the right contract by themselves.

This corrects a contradiction between the plans. The older plan said scene count was not the issue and estimated 10–16-second reference scenes with a beat every 2–4 seconds (`VIDEO_AESTHETIC_PLAN.md:517-543,610-624,746-750`). The newer frame-level audit counts **scaffolds/layouts**, **content swaps**, and **micro-beats** separately: R2 has one dominant scaffold for about 125 seconds, 18 layouts, and only five hard cuts; R3 has 32 numbered scaffolds and 31 cuts; R5 has 33 scaffolds but 63 substates (`MOTION_PACING_PLAN.md:47-49,59-62,76-79`). The newer measurements supersede the older pacing estimate, but they do not imply one mounted component per scaffold or one cut per beat.

This is not solely a TTS-speed discrepancy. The request of 45 is first floored to 90 seconds and at least ten scenes (`orchestrator/lib/video/scenePlan.js:143-156`), while the prompt budgets narration at 150 wpm (`scripting-pipeline/src/promptBuilder.ts:117`) and actual scene duration is then replaced with measured WAV duration (`orchestrator/generate-video.js:156-216`). The mismatch has three contributors: request semantics, text budget, and voice duration. There is a validation mismatch the phase plan must include: the orchestrator calls `generateScript` without its narrative-arc config (`orchestrator/lib/video/scriptGen.js:97-108`), so it receives the default `minSceneCount: 1`, `maxSceneCount: 100` (`scripting-pipeline/src/pipeline.ts:52-57`; `types.ts:109-133`). Conversely, `checkVariety` rejects a script using one component type throughout (`validation.ts:228-239`), and the prompt explicitly asks for varied types (`promptBuilder.ts:120`); both push against the proposed persistent-scaffold design. Changes to `scripting-pipeline/src` also require its compiled `dist` to be rebuilt before `scriptGen.js` uses them (`orchestrator/lib/video/scriptGen.js:54-65`).

## Revised implementation plan

1. **Define a v2 timeline contract before changing scene count.** Distinguish `chapter` (narrative arc), `visualHost` (persistent layout/component instance), and `event` (time, target, operation, value, semantic word or sentence anchor). A chapter may contain several hosts; a host may span many narration sentences; an event may be a reveal, text/state update, highlight, counter, connector, or host replacement. Keep v1 as the default until v2 proves a real render. Make event IDs and ordering deterministic; validate content types against the catalog. Use explicit cumulative state or replayable event history so seeking to any timestamp gives the same frame. This addresses R2's persistence and R5's substates without inventing a cut for every beat.
2. **Prototype continuity on one reusable host.** Choose `node-graph-diagram` or `deployment-dashboard` with two or three states and one full-chapter mount. Compare last/first frames around event boundaries and random-seek snapshots. A second host is mounted only when there is an actual layout change; support short fades or hard cuts separately. If a multi-mount strategy is preferred, materialize full state on the new mount at `t=0` and test equivalence; never assume `enter:"continue"` copies state. Keep the persistent HUD/captions/mascot at the root (`composeHtml.js:638-661,728-745`).
3. **Fix the temporal contract and audio in one measured slice.** Set length in *final output seconds* and have the planner budget words and authored duration using measured TTS and post speed; eliminate the silent 45→90 floor. Measure F5 at several speeds using the actual cloned/default voice, record WPM and intelligibility, then choose TTS and post speed. Test silence trim with shifted alignment and the first-frame baseline. Use global word indices or occurrence-aware anchors, with an explicit drift check against the generated audio. Keep one audio timeline even if synthesis uses several chunks.
4. **Make item timing a capability, not a property-name trick.** Registry metadata should declare which component operations and item identities are supported. Adapt pipe-string and JSON-list components explicitly. Validate that every event addresses a declared operation and real item, that content is not overwritten, and that multiple events for the same item are ordered. Start with a few commonly selected components and quantify actual word anchoring and visible beats before extending the catalog (`scripting-pipeline/src/componentCatalog.ts:51-66,105-116` currently loads only generic manifest variables).
5. **Build layered QA and bounded recovery.** First validate script facts/visual state graph before TTS; then validate alignment, duration, first-frame content, and event reachability before render; run `hyperframes check` and transition/random-seek snapshots; finally run calibrated pacing/audio diagnostics and a visual spot check on the MP4. Classify failures as script, timing, component/layout, rendering, or aesthetic. Repair the smallest affected artifact once or a bounded number of times, preserve the failed output and reason, and surface a visible failed/needs-review state. Regenerate the full script only for script-caused failures. An average beats/min target alone must not reject R2-style long-lived scaffolds or accept busy captions/blinks as useful content.
6. **Finish click-to-local-video autonomy before scheduling or posting.** Pass a single validated job config from API through render engine to CLI (including speed, theme, mascot, handle and target final length); choose real defaults rather than `@example` (`server.js:267-275`; `renderEngine.js:79-107`; `generate-video.js:80-95`). Persist queue stage, inputs, outputs, failure classification and attempts so a restart can reconcile or retry safely. Replace the current SpongeBob source before any autonomous distribution: it is hardwired in `composeHtml.js:206` and the generated composition, while the earlier plan describes reference videos using Rick Sanchez (`VIDEO_AESTHETIC_PLAN.md:516`); provenance or usage rights were not established by this code review. Publishing remains a separate opt-in project after local output quality is reliable.

## Latency, cost, and release gates

The observed job took 12m47s for ten sequential TTS+alignment calls plus Gemini, checking, rendering and ffmpeg; the persisted run has no per-stage timing breakdown. Therefore neither "three times the scenes costs three times as much" nor "four narration chunks will offset it" is established. Instrument wall time and resource use per stage, output duration, Gemini attempt count/input-output tokens, F5/WhisperX calls, render frames, and retry cause before setting a throughput/cost target. The script repair loop allows three full attempts (`scripting-pipeline/src/types.ts:109-117`; `pipeline.ts:63-95`) and repeats the full catalog and prior invalid response (`promptBuilder.ts:112-143`), so a 25–40-scene response can materially increase tokens and retry latency. The control panel serializes video jobs on one GPU (`server.js:125-133,166-198`); parallel topic-button clicks queue behind each other.

Acceptance should be a small, explicit pilot: current hash-collision topic plus two unlike topics, including a long-lived diagram and a cut-heavy explanation. For each, record final duration vs request, onset silence, word/event offset, empty content at cut/host entry, random-seek equality, frozen semantic holds, component/layout errors, and human review of narration and factual correctness. The pacing plan's reference bands (`MOTION_PACING_PLAN.md:85-101`) are useful targets, not hard universal thresholds until the detector is calibrated against all five reference logs. Publish no automatic success merely because `hyperframes check` reports zero errors; the current orchestrator only gates those five technical sections (`generate-video.js:255-276`).

**Answer to the architecture question:** no new project and no wholesale renderer replacement. Do make a substantial v2 content/timing contract and a durable QA/job layer. Start with a one-host event prototype and measured voice timing; only increase mounted scene count when a layout change actually calls for it.
